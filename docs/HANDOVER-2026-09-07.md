### 0. CRITICAL — the website's "read-only" database credential is a superuser

This is the most serious thing found today and it needs the Atlas console,
which is why it is yours. Verified live:

```
MONGO_URI_READONLY -> user "ctiaze"      roles: [atlasAdmin@admin]
MONGO_URI_WRITE    -> user "skopnix_web" roles: [readWrite@ctiaze]
```

`MONGO_URI_READONLY` — the credential the PUBLIC website runs on — is the
pipeline's `atlasAdmin` superuser, with the same password as the engine's
`MONGO_URI` GitHub secret (both hash to `b18ae13e...`). `atlasAdmin` can drop
any collection in the project. `lib/db.ts` asserted in a comment that this was
"a dedicated READ-ONLY user"; it never was.

Why it matters: every other finding on this list assumed a blast radius that
does not exist. Any environment disclosure, dependency compromise, or Vercel
account compromise on the website hands an attacker destructive control of the
whole cluster — 13,000 items, the actor roster, the signup list, the visit log.

I did not fix it because the fix requires creating a database user and typing
its password into the Atlas and Vercel consoles, and I do not enter credentials
into forms.

Do this, in order:
1. **Atlas → Database Access → Add New Database User.** Name `skopnix_read`,
   autogenerate the password, role: **`read`** on database **`ctiaze`** only
   (not `readAnyDatabase`, not a project role).
2. **Vercel → skopnix → Settings → Environment Variables** → replace
   `MONGO_URI_READONLY` with the new user's URI. Redeploy.
3. Verify: `node --env-file=.env.local scripts/check-db-privileges.mjs`
   (update your local `.env.local` too). It exits 0 only when the credential
   holds nothing but `read`. It currently exits 1.
4. **Then** rotate the `ctiaze` user's password — it now sits in two `.env`
   files and a GitHub secret — and update `MONGO_URI` in the engine repo's
   secrets in the same sitting, or the 2-hourly pipeline breaks.
5. Finally, demote `ctiaze` from `atlasAdmin` to `readWrite@ctiaze`. Nothing
   the pipeline does needs project-admin.

Also worth confirming while you are in there: the Atlas IP access list is
cluster-wide and probably `0.0.0.0/0`.


### 1. DNS at Spaceship (skopnix.com) — the highest-value 10 minutes here
Right now **anyone can send mail as `hello@skopnix.com`** — the address printed
in `/.well-known/security.txt` — and **no mail sent to it can ever arrive**,
because the domain has no MX at all. For a threat-intel brand whose product is
trusted attribution, a forged "skopnix advisory" is the cheapest possible attack.

Add these records exactly:

| Type | Host | Value |
|---|---|---|
| TXT | `@` | `v=spf1 -all` |
| TXT | `_dmarc` | `v=DMARC1; p=reject; adkim=s; aspf=s; fo=1; rua=mailto:<a mailbox you read>` |
| TXT | `*._domainkey` | `v=DKIM1; p=` |
| MX | `@` | priority `0`, value `.` (RFC 7505 null MX) |
| CAA | `@` | `0 issue "letsencrypt.org"` |
| CAA | `@` | `0 issuewild ";"` |
| CAA | `@` | `0 iodef "mailto:<a mailbox you read>"` |

Then EITHER stand up real inbound mail (and relax SPF to that provider's
`include:`) OR change the `Contact:` line in `public/.well-known/security.txt`
to an address that receives mail. Do not leave both as they are.

Also enable **DNSSEC** in the Spaceship panel. Without it and without CAA, a DNS
hijack converts straight into a valid certificate from any of ~130 CAs.

## KNOWN, NOT FIXED

- **CSP keeps `script-src 'unsafe-inline'`.** No reachable inline-injection sink
  exists today (every HTML sink is escaped), so this is latent. A real fix needs
  nonces via middleware, which this project deliberately avoids for its
  per-request cost. Revisit if any raw-HTML sink is ever added.
- **The rate limiter is per-serverless-instance.** A rotating-IP or
  multi-instance caller is not bounded by it. `lib/ratelimit.ts` already has an
  Upstash-backed path — set `UPSTASH_REDIS_REST_URL` / `_TOKEN` to switch the
  waitlist and beacon onto a shared counter.
- **Stories are still mostly RSS ledes** (106 of 200 truncated) and 64 of 97
  vuln items carry no CVE because extraction reads the feed lede, not the
  article body. This is the biggest remaining quality gap and it is an engine
  change, not a website one.
- **Dossier roster cruft.** `/actors/agl0bgvycg` is base64 "hitler"; some
  ransomware.live stubs carry an engine-written brief. A quality gate (ATT&CK or
  MISP id, or ≥2 sources) would cut the "1,373 dossiers" number and raise it.
- **The archive has a five-day hole, 22–31 Aug.** Worth a public status page.

- **Exports per dossier**: an ATT&CK Navigator layer, a STIX 2.1 bundle

## New in the engine
- `--backfill` ran over all 13,069 archived items: 1,555 links, 1,372 events.
- `actor-track.yml`, daily at 05:41 UTC: recompute activity, detect changes,
  re-pack. Mongo only — no LLM, no paid API.
- The CVE **evidence gate**: a link is written only when the actor and the CVE
  fall within 50 words, the window carries an exploitation verb, and it carries
  no roundup language — and the matching sentence is stored and displayed.

## What the backfill taught us (worth reading before extending this)
Running against 13,000 real articles found three false-positive classes no unit
test would have caught:
1. Leak-site crews literally named "unknown", "global", "payload" matched every
   article using the word — 86 dispatches credited to "unknown". Primary names
   are now held to the same precision standard as aliases, except on sources
   that state the actor in a field (a leak-site row), where the bare name is
   trustworthy.
2. MISP lists **CHROMIUM** as an alias of Earth Lusca, so eight Google Chromium
   CVEs were attributed to it, each with a well-formed evidence quote that never
   named the group. CVE attribution now uses a stricter key set: primary name
   plus aliases that are multi-word or carry a designator shape.
3. "obscura" matched inside "Delta Obscura". Curated stoplist. **Not fully
   solved** — a single-token name can still sit inside a longer proper noun.

The whole archive now yields **seven** CVE attributions, every one citable:
APT28/CVE-2026-21509 (Zscaler), ShinyHunters/CVE-2026-35273 (GTIG),
DragonForce/CitrixBleed 2, Void Blizzard (two), Qilin/PAN-OS, LockBit/ActiveMQ.

## Known, and NOT fixed
- **`actor_pack.similar` is empty.** Its source field `threat_actors.similar_actors`
  was already empty before today, so the daily re-pack propagated that. The
  section was already hidden by a filter that drops sub-0.8 semantic-only matches
  as noise (a reviewer's call, and the right one), so nothing visible was lost —
  but regenerating it needs the paid `ops/` batch, OR a cheaper deterministic
  version computed from shared techniques and tools, which would be better data
  anyway. Worth doing.
- **A cold render of `/cve/<id>` or `/api/v1/actors` takes ~30s** (NVD plus the
  roster blob) against a 60s function ceiling. Warm, both serve in ~0.3s from
  the CDN and they cache for an hour, so this only bites once per hour per
  route — but it is closer to the ceiling than it should be.
- **Weaponization lag** is implemented but almost always absent: items are
  clustered by their first CVE, so the NVD record and the stories about it are
  one document dated at disclosure, and a lag from that is a guaranteed zero.
  A real figure needs a per-article date on items.
